Layer 10 · Finding the seams

The Game Moved Into the Toolkit

Getting back to tools meant looking at the application we had built. I already knew the API was doing too much. Moving Encounter into the toolkit was a useful step, but I knew it was still an application. I hoped bringing that work together would make the seams easier to see.

01The older API
More than accepting a request

A move was a procedure in the API

The API accepted the request, but it also helped run the game. In the older movement path it gathered room and wall data, checked the path, calculated movement cost, changed positions, saved state, and published the result. That was not just translating a request into toolkit calls.

02The newer route
Give the host an encounter operation

The API could ask Encounter to move

For movement, the API’s outer routine became load, call Move, persist. Encounter coordinated the path, combat movement spending, position updates and player-specific events. Rulebook adapters still lived in the API. Even so, the server could invoke an encounter operation instead of owning that whole procedure.

A clearer host boundary was progress. It was not the final shape.
03Inside the toolkit
The location did not make it generic

The root package still knew D&D

Encounter lived at the toolkit root, but depended directly on the D&D rulebook. D&D gameplay and more general infrastructure still shared one module. There were interfaces, but the application was still bundled together. I hoped that having the work here would make its seams easier to see.

A module boundary is not automatically a useful tool boundary.
04The limit of the move
Concentrating the work, not declaring it finished

Seeing the shape was only a start

I wasn’t mistaking the application for a toolbox. I knew the difference, and moving it was still worth doing. The work was closer to the rules and the pieces it used. I wanted to examine what belonged together and what might deserve a life of its own.

Knowing the problems did not tell me which boundary would matter most when I tried to build something different. That would take more than looking at the code.

I could see the architectural problems.
I hadn’t yet felt how much they would get in the way of what I wanted to build.

Evidence trail

I already knew the API did too much. I knew I was moving an application into the toolkit and hoped its seams would become easier to see. The May SDK direction records the intended transfer of lifecycle, dispatch and player-facing projection. The root skeleton began in May; its growth and adoption were not one move dated to my personal return.

The earlier API movement routine carries path, budget and position work. The later MoveEntity route calls a loaded Encounter and persists its result. That API snapshot pins encounter v0.24.4, which resolves to the toolkit movement implementation shown here.

This was not the disappearance of all host-side work. The API still supplied rulebook adapters, Character loading/persistence and NPC-turn dispatch. The toolkit’s module dependencies and July placement decision document the D&D coupling and mixed responsibilities. That decision moved no code.

Historical source and dependency pins were inspected; no historical build, test suite or complete gameplay walk was run. This note ends before the later authoring pressure and composable rebuild. Diagrams explain selected responsibilities, not a complete system inventory.
